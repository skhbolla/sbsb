[External Link ↗](https://leetcode.com/problems/3sum/)

## Description

Given an integer array `nums`, return all the triplets `[nums[i], nums[j], nums[k]]` such that `i != j, i != k, and j != k`, and `nums[i] + nums[j] + nums[k] == 0`.

*Notice that the solution set must not contain duplicate triplets.*

**Constraints:**  
* `3 <= nums.length <= 3000`
* $-10^5 <= nums[i] <= 10^5$

## 1. Bruteforce Approach

### Intuition

Since the goal is to find all triplets $(nums[i], nums[j], nums[k])$ that sum to zero, the most direct method is to generate every possible combination of three elements from the array.

* **Selection**: We use three nested loops to pick three different elements.
* **Constraint**: We ensure the indices are distinct (handled by the loop ranges $i+1$ and $j+1$).
* **Verification**: We check if the sum equals zero.
* **Deduplication**: Because the input array can contain the same value at different indices, we sort the found triplet and store it in a Set to ensure our final list only contains unique combinations of numbers.

#### Why Limiting Loops Does Not Avoid Duplication

This is the most subtle part of the problem. In the `2Sum` problem (where you return indices), the constraint `j = i + 1` is enough because indices are inherently unique. However, 3Sum asks to return unique values (not indices), and values are ***not unique*** in the input.

##### The "Twin" Scenario
Consider `nums = [-1, -1, 0, 1]`.
This approach will execute the following valid index combinations where `i < j < k`:

1. **Index (0, 2, 3)** : Values `nums[0]=-1, nums[2]=0, nums[3]=1`. Sum = 0. `Triplet: [-1, 0, 1]`.
2. **Index (1, 2, 3)** : Values `nums[1]=-1, nums[2]=0, nums[3]=1`. Sum = 0. `Triplet: [-1, 0, 1]`.

Even though the loops correctly ensured we never reused the same index (index 0 was never used twice), the result is the same because index 0 and index 1 are "twins" - they hold the same value.

In `2Sum`, you usually stop after the first match or return indices, so this isn't an issue. In 3Sum, you are collecting all solutions, so without the `Set`, you would return `[[-1, 0, 1], [-1, 0, 1]]`, which violates the "unique triplets" rule.


### Implementation
```python
def bruteforce(self, nums: list[int]) -> list[list[int]]:
        '''
        Explore all possible triplets and add the zero sum triplets to a set for de-duplication.
        '''
        sol = set()
        for i in range(0, len(nums)):
            for j in range(i+1, len(nums)):
                for k in range(j+1, len(nums)):
                    if nums[i] + nums[j] + nums[k] == 0:
                        # No need to check i!= j and i != k and j != k
                        # because the loop ranges already guarentee it
                        x = sorted([nums[i], nums[j], nums[k]])
                        sol.add(tuple(x))

        return [list(i) for i in sol]
```

### Complexity Analysis

* **Time Complexity:** $O(n^3)$
  * **Three nested loops** is $(n * (n-1) * (n-2))/ (3 * 2 * 1)$ iterations which is asymtotically $O(n^3)$.
  * **Sorting each triplet** is $O(n log n)$ where `n = 3` i.e $O(3 log 3)$ which is constant time $O(1)$.
  * **Set Insertion** is $O(1)$ on average
  $$ O(n^3 * 3 log 3 * 1) \equiv O(n^3) $$

* **Space Complexity:** $O(m)$ where $m$ is the number of unique triplets
  * `set` has to store $m$ unique triplets, which in worst case can be proportional to $n^2$.
  * Output list is **NOT** counted towards Space complexity.

### Low-Level Implications: 

* With three nested loops, you are constantly re-scanning the same memory addresses. As `n` grows, the inner loop ($k$) finishes and the middle loop ($j$) moves forward. While the CPU tries to predict your next move (branch prediction), the sheer volume of redundant comparisons (roughly $\frac{n^3}{6}$) means the CPU spends more time waiting for data to move from RAM to Cache than actually performing the addition.

## 2. Pre-Sorted Bruteforce - (The "Lazy" Optimization)

### Intuition

In the raw brute force, we are forced to sort every valid triplet (`x = sorted([nums[i], nums[j], nums[k]])`) ($O(3 \log 3)$) and convert it into a tuple before adding it to a Set. While $3 \log 3$ is technically $O(1)$, performing this thousands of times inside the "hot path" of the inner loops adds significant computational weight. By sorting the entire input array once ($O(n \log n)$) at the start, we ensure that any triplet picked via indices $i < j < k$ is naturally sorted.

**Note** : While this approach doesn't lower the $O(n^3)$ theoretical upper bound, we get the following benefits out of "pre-sorting" the array.

* **Eliminating In-Loop Sorting**: Since the source array is sorted, `nums[i], nums[j], and nums[k]` are already in non-decreasing order. We can discard the sorted() call and the temporary list allocation entirely, directly adding the values as a tuple to our Set.
  
* **Predictability**: Pre-sorting creates a monotonic trend in the sums. This allows the CPU's Branch Predictor to start recognizing patterns in the `sum == 0` check, leading to fewer pipeline stalls than the random distribution of an unsorted array.
  
* **Constant Factor Reduction**: By sorting once, we move the "ordering" logic out of the $O(n^3)$ loops. This reduces the number of instructions executed per iteration, allowing the CPU to focus purely on the arithmetic sum and the hash-set insertion.

#### Low Level Systems Impact

Sorting the array organizes the data in memory, which immediately changes how the hardware interacts with the software

* **Branch Prediction & Pipelining**: Modern CPUs use a pipeline to execute multiple instructions at once. They guess the outcome of `if` statements to keep the pipeline full. In an unsorted array, the sum of three numbers is essentially random, causing frequent Branch Mispredictions. These mispredictions "stall" the CPU, forcing it to flush the pipeline and restart. In a sorted array, the sums follow a monotonic trend, allowing the branch predictor to achieve near-perfect accuracy and keeping the instruction flow "hot."
  
* **Cache Locality (Spatial & Temporal)**: When the CPU fetches nums[i], it doesn't just grab 4 bytes; it grabs a 64-byte Cache Line. By iterating through a sorted array, we maximize Spatial Locality. Because $j$ and $k$ follow $i$ in a linear, contiguous fashion, the data they require is almost certainly already sitting in the "hot" L1 cache. This ***prevents Cache Thrashing***, where the CPU is forced to repeatedly overwrite the cache with new data because the access pattern is too scattered to be useful.


### Implementation
```python
def sorted_bruteforce(self, nums: list[int]) -> list[list[int]]:
        '''
         By pre-sorting the array , we can improve the real world
         performance of bruteforce (although TC remains same).
        '''
        nums.sort()
        s = set()
        sol = []
        for i in range(0, len(nums)):
            for j in range(i+1, len(nums)):
                for k in range(j+1, len(nums)):
                    if nums[i] + nums[j] + nums[k] == 0:
                        s.add(tuple([nums[i], nums[j], nums[k]]))
        return [list(i) for i in s]
```

### Complexity Analysis

* **Time Complexity:** $O(n^3)$
  * We still traverse all triplets, but the constant factor ($c$) is reduced by removing the internal sort.
* **Space Complexity:** $O(m)$
  * We still rely on a Hash Set to store $m$ unique triplets to handle duplicate values in the input

## 3. Optimized Sorted Brute Force - (Skip and Early break)

### Intuition

The previous approach still suffers from "Search Blindness" and "Object Bloat" because it relies on a Hash Set to catch duplicates after they are formed. In this approach, we leverage the sorted structure to proactively skip redundant work and prune the search space entirely.

**Note** : While this approach doesn't lower the $O(n^3)$ theoretical upper bound, we get the following benefits.

* **Deduplication via Skip Logic**: Instead of using a Hash Set to filter duplicates, we use the sorted property to skip them. If `nums[i] == nums[i-1]`, we know that any triplet starting with the current value was already explored. This replaces the expensive set.add() routine which involves *calculating a SipHash, navigating a hash table, and managing memory resizing (reallocs)* with a single $O(1)$ Register Comparison.

* **The Early Break (Pruning)**: Sorting provides a mathematical floor. In a sorted array, if $nums[i] > 0$, then $nums[j]$ and $nums[k]$ must also be positive. Since three positive integers cannot sum to zero, we can break the outermost loop immediately. This prunes a massive percentage of the search space that an unsorted brute force would be forced to traverse.
  
* **Constant Factor Reduction**: We replace a complex data structure (the `Set`) with simple if statements. By keeping the "hot path" of the code strictly within the CPU's Arithmetic Logic Unit (ALU), we allow the loop to run at the maximum clock speed of the processor without managing heap objects.

#### Low Level Systems Impact

This approach is fundamentally about "playing nice" with modern hardware architecture by aligning data access with how a CPU actually breathes.

* **Eliminating Hash Table Overhead**: A set (Hash Set) requires the CPU to jump out of its tight loop to execute complex hashing functions and manage memory buckets. By removing the Set, we eliminate Instruction Cache (I-Cache) misses and keep the CPU focused on a tiny, extremely fast loop of additions and comparisons that can stay entirely within the L1 Instruction Cache.

* **Register-Level Execution**: Without a Set, we no longer need to allocate tuple objects or manage a dynamic hash table on the Heap. The three numbers being summed can stay in the CPU Registers, making the "zero check" happen at the speed of the processor's clock cycle rather than being throttled by memory allocation and pointer dereferencing.

* **Branch Prediction Optimization**: Because we've added specific if checks for duplicates and the break for positive numbers, we've made the code's behavior even more deterministic. The Branch Predictor can "see" the boundaries of the data more clearly, ensuring the instruction pipeline stays saturated.

### Implementation
```python
def optimized_sorted_bruteforce(self, nums: list[int]) -> list[list[int]]:
        nums.sort()
        sol = []
        n = len(nums)

        for i in range(n):
            # Early Break: Smallest number > 0 means no zero sum possible
            if nums[i] > 0:
                break
            # Skip Logic: Avoid re-processing the same 'i' value
            if i > 0 and nums[i] == nums[i-1]:
                continue

            for j in range(i + 1, n):
                # Skip Logic: Avoid re-processing the same 'j' value
                if j > i + 1 and nums[j] == nums[j-1]:
                    continue

                for k in range(j + 1, n):
                    # Skip Logic: Avoid re-processing the same 'k' value
                    if k > j + 1 and nums[k] == nums[k-1]:
                        continue

                    total = nums[i] + nums[j] + nums[k]
                    if total == 0:
                        sol.append([nums[i], nums[j], nums[k]])
                    elif total > 0:
                        # Since it's sorted, if total > 0, increasing k won't help
                        break
        return sol
```

### Complexity Analysis

* **Time Complexity:** $O(n^3)$
  * The theoretical worst-case remains the same, but the "real world" time is drastically lower due to pruning and the removal of hashing overhead.
* **Space Complexity:** $O(1)$
  * Space to store the solution is not considered.
  * We have completely eliminated the $O(m)$ space required by the Hash Set.

## 4. Two Pointers Approach 

### Intuition

While the previous approach optimized the "real-world" runtime, it was still conceptually bound by a cubic search space. The breakthrough comes from recognizing that once we fix the first element $i$, we are simply solving the Two Sum problem on the remaining sorted sub-array. By using two pointers that converge from both ends, we collapse the nested $j$ and $k$ loops into a single linear scan.

Note: This is a fundamental algorithmic shift that finally lowers the theoretical Time Complexity to $O(n^2)$.

* **Converging Search Strategy**: Instead of resetting a third loop ($k$) for every increment of the second ($j$), we place left at $i+1$ and right at the end of the array. If the total is too small, we move the left pointer to the right to increase the sum. If the total is too large, we move the right pointer to the left to decrease it. This ensures we touch each element in the sub-array at most once per $i$
  
* **Dynamic Deduplication**: Since we no longer have a Hash Set, we must handle the "multi-solution" nature of 3Sum manually. When a match (total == 0) is found, we record it and then "burn" through any adjacent identical values for both left and right. This ensures that we don't report the same value combination twice for a fixed $i$.
  
* **The "Double Skip" Logic**: By skipping duplicates at the $i$ level and again at the left/right level, we guarantee a unique result set. This logic is much more efficient than post-processing with a Set because we never generate the redundant triplets in the first place.


#### Low Level Systems Impact

This approach represents the pinnacle of balancing algorithmic efficiency with hardware-aware programming.

* **Linear Memory Access (Stride Optimization)**: The two-pointer scan moves linearly from both ends toward the middle. This access pattern is incredibly "friendly" to the CPU Hardware Prefetcher. Because the memory addresses follow a predictable stride, the prefetcher can warm up the L1 Cache with the next values before the pointers even reach them, effectively hiding memory latency.
  
* **Optimal Pipeline Utilization**: By replacing the $O(n^3)$ triple loop with a converging $O(n^2)$ scan, we reduce the total instruction count by orders of magnitude. The inner loop's condition `(left < right)` and the sum checks are extremely simple, allowing the CPU to maintain high Instruction-Level Parallelism (ILP) and keeping the execution pipeline saturated.
  
* **Branch Predictor Accuracy**: In the two-pointer phase, the sum changes monotonically as pointers move. This trend allows the TAGE branch predictor to accurately anticipate whether the next move will be a `left += 1` or a `right -= 1`. This minimizes pipeline flushes and keeps the "hot path" flowing at maximum clock speed.

### Implementation
```python
def optimal(self, nums: list[int]) -> list[list[int]]:
        nums.sort()
        sol = []
        n = len(nums)

        for i in range(n):
            # Early Break and Skip Logic for 'i'
            if nums[i] > 0:
                break
            if i > 0 and nums[i] == nums[i-1]:
                continue

            # Initialize Two Pointers
            left, right = i + 1, n - 1

            while left < right:
                total = nums[i] + nums[left] + nums[right]

                if total < 0:
                    left += 1
                elif total > 0:
                    right -= 1
                else:
                    # Match found
                    sol.append([nums[i], nums[left], nums[right]])
                    
                    # Move pointers and skip duplicate twins to avoid redundant results
                    while left < right and nums[left] == nums[left + 1]:
                        left += 1
                    while left < right and nums[right] == nums[right - 1]:
                        right -= 1
                    
                    # Final shift to next unique values
                    left += 1
                    right -= 1
        return sol
```

### Complexity Analysis

* **Time Complexity:** $O(n^2)$
  * The outer loop runs $n$ times. For each $i$, the inner two-pointer scan covers the remaining $n-i$ elements in a single pass. $O(n \times n) = O(n^2)$.
* **Space Complexity:** $O(1)$
  * Excluding the space for the output list, we only use a constant amount of extra memory for pointers and sum variables.
  * No extra space for sorting is counted (assuming in-place sort).

## TLDR

1. **Raw Brute Force ($O(n^3)$)** 
   * **The Logic**: Triple-nested loops scan every index combination.
   * **Deduplication**: Reactive (we handle duplicate after we find them instead of actively avoiding them). Each found triplet is sorted and hashed into a `set()`.
   * **The Bottleneck**: High Constant Factors. The CPU is throttled by constant heap allocations, SipHash calculations, and object overhead for every match.
   
2. **Pre-Sorted Brute Force ($O(n^3)$)** 
   * **The Logic**: Sort the entire array once ($O(n \log n)$) at the start.
   * **The Improvement**: Since the input is ordered, index-order selection ($i < j < k$) yields triplets that are already sorted.
   * **The Systems Win**: Eliminates thousands of `sort()` calls inside the hot path. It trades a one-time organizational cost for a massive reduction in instructions per iteration.
   
3. **Optimized Sorted Brute Force ($O(n^3)$)** 
   * **The Logic**: Activates the sorted structure to "short-circuit" the logic using Skip Logic and Early Exit.
   * **Deduplication**: Proactive. Deletes the Hash Set entirely. We skip duplicates using $O(1)$ register comparisons `(if nums[i] == nums[i-1]: continue)`.
   * **The Systems Win**: *Pruning*. The `if nums[i] > 0: break` terminates the search the moment a sum becomes mathematically impossible, saving billions of cycles. This keeps the execution inside the L1 Cache and ALU, avoiding the "Memory Wall."
   
4. **Two-Pointer Approach ($O(n^2)$)** 
   * **The Logic**: Fixes $i$, then replaces the nested $j$ and $k$ loops with a *single converging scan* (`left` and `right` pointers).
   * **The Improvement**: Pointers move toward each other once per $i$. We "burn" through duplicate values on the fly to maintain uniqueness
   * **The Algorithmic Win**: Collapses complexity from *Cubic to Quadratic*.
   * **Hardware Impact**: Predictable linear strides maximize the *Hardware Prefetcher's efficiency* and ensure near-perfect Branch Prediction accuracy.
